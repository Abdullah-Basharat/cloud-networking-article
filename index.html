Section 01

What is a VPC?

Before your application can exist in the cloud, you need a network for it to live in. That network is a VPC Virtual Private Cloud.

Think of AWS as a massive city with thousands of buildings. Your VPC is your private building inside that city. You decide who can enter, how floors are arranged, and which rooms talk to each other. Other buildings cannot see inside yours.

Real world analogy
City = AWS
Your building = Your VPC
Building IP range = CIDR block
Other buildings = Other customers
AWS terms
AWS Region = us-east-1
VPC CIDR = 10.0.0.0/16
65,536 private IPs available
Fully isolated by default

Fig 1 Your VPC is a fully isolated private network. Other AWS customers cannot see or access it.

Warning Default VPC AWS gives you a Default VPC with everything public. Never use it in production. Always create a custom VPC where you control the networking from scratch.
CIDR cheat sheet 10.0.0.0/16 -- 65,536 IPs typical VPC size 10.0.1.0/24 -- 256 IPs typical subnet size 10.0.1.5/32 -- 1 IP one specific address Rule: smaller /number = MORE IPs bigger /number = FEWER IPs
Section 02

Subnets Dividing your network into layers

Your VPC is one big IP range but you do not put everything in one place. You divide it into subnets: smaller IP ranges for different purposes.

Think of subnets as floors inside your building. The reception floor is open to visitors. The work floor is for employees only. The server room is the most restricted.

Fig 2 Three subnet tiers. Each resource lives in the subnet that matches its security requirement.

Key insight What makes a subnet public or private is NOT a toggle in AWS. It is determined by whether its Route Table has a route pointing to an Internet Gateway covered in the next section.
Section 03

Internet Gateway & Route Tables

An Internet Gateway (IGW) is the main door of your VPC the connection between your private network and the public internet. Without it, nothing inside your VPC can reach the internet.

A Route Table is like a signboard. It tells every packet of traffic: "if you are trying to reach this destination, go in that direction." Every subnet gets a route table attached to it.

Fig 3 The route table entry "0.0.0.0/0 → IGW" is the one thing that makes a subnet public.

Section 04

Security Groups The bouncer at every door

Private subnets block the internet but what about traffic inside your VPC? Any resource in the same VPC can potentially reach any other resource. That is where Security Groups come in.

A Security Group is a firewall attached directly to a resource EC2, RDS, Lambda. It controls exactly which traffic can come IN and go OUT on which ports. They work as a whitelist: everything is denied by default, you only add what you want to allow.

Common mistake "My database is in a private subnet so it is safe." Not quite. Private subnets block internet traffic. But your Frontend EC2 in the same VPC can still reach your database unless a Security Group blocks it. Both layers are always needed.

Fig 4 Every resource has its own Security Group. Only explicitly defined traffic flows between them.

Security Group rules Nginx SG -- IN: 80, 443 from internet (0.0.0.0/0) Frontend SG -- IN: 3000 from Nginx SG ID only Backend SG -- IN: 8000 from Nginx SG ID + Frontend SG ID Database SG -- IN: 5432 from Backend SG ID only Use Security Group IDs for internal resource-to-resource rules. CIDR is for internet traffic and specific IP ranges only.
Section 05

Complete production architecture

Now let us see everything working together. Here is the full journey of a user request from browser to database with every networking concept playing its role.

Fig 5 The full request journey. Every layer is protected. The internet only ever touches Nginx.

Why Nginx in front? Without Nginx, your app server's IP would be exposed to the internet. With Nginx, the internet only sees one IP address. Your actual app servers are invisible. Nginx also handles SSL termination, rate limiting, and load distribution.
Section 06

VPC Peering Connecting two VPCs

By default, VPCs are completely isolated from each other even in the same AWS account. VPC Peering creates a direct private connection between two VPCs so their resources can communicate as if on the same network.

Three steps to set up VPC Peering 1. Send a peering request from VPC A to VPC B
2. Accept the request in VPC B
3. Update route tables in BOTH VPCs without this step traffic will not flow even if the peering exists

Fig 6 VPC Peering works well for 2–3 VPCs. With more, it becomes unmanageable.

Section 07

Transit Gateway Networking at scale

Transit Gateway solves the peering problem with a simple idea: instead of connecting every VPC to every other VPC, all VPCs connect to one central hub. Think of it as a hub airport all flights pass through it instead of flying directly city-to-city.

Fig 7 Transit Gateway replaces a tangled mesh with a clean hub-and-spoke. One attachment per VPC.

Key takeaways

1
VPC is your isolated private network. Never use the AWS default VPC in production always build a custom one.
2
Subnets are IP ranges inside your VPC. Public vs private is decided by the Route Table not a checkbox.
3
Internet Gateway + Route Table is the combination that gives a subnet internet access. Both are required.
4
Security Groups are per-resource whitelists. Private subnet blocks the internet. Security Group blocks internal VPC threats. You need both.
5
Nginx as reverse proxy means the internet only ever sees one IP. Your actual application servers are completely hidden behind it.
6
VPC Peering for 2–3 VPCs. Transit Gateway for anything larger or when you need to connect an on-premise office network.
